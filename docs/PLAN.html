결론 — 저장 문제는 해소됨 주소 문자열 자체를 저장하는 데는 아무 제약이 없다(공고문에 실린 공공 정보다). 제약은 지오코딩 API 응답에만 걸린다. 따라서 좌표를 API로 조회하지 않고 위치정보 요약DB를 내려받아 자체 좌표 테이블로 보유하고, 공고 주소와 오프라인으로 조인한다. 쿼터도 저장 제약도 사라진다.

실시간 API 방식은 애초에 성립하지 않는다. 공고 지도 한 장에 마커가 476개이므로 페이지 1회 열람에 476콜, 일 방문 84명이면 40,000건 쿼터가 소진된다.

확인 필요 항목

  • 마이홈포털 3종 API의 실제 응답 필드 — 각 데이터셋의 붙임1. 요청 파라미터 코드.xlsx 및 상세기능명세 다운로드. 응답에 호실 단위 주소나 좌표가 포함되면 파이프라인이 통째로 짧아지므로 착수 순서상 최우선.
  • 위치정보 요약DB 신청 승인 소요기간 — juso.go.kr 신청서 제출 후 소관 자치단체·행안부 이용목적 심사. 소요일수가 확인되지 않았고 Phase 1 일정의 선행 조건이므로 즉시 신청부터 걸어 둘 것.
  • 공고문 첨부파일(HWP/PDF)의 재가공·재배포 허용 범위 — LH·SH 각 사이트 이용약관, robots.txt, 저작물 이용 안내 확인.
  • 마이홈포털 API 운영계정 심의 통과 조건 — 심의 기준·소요기간. 개발계정 1,000건/일로는 전국 백필 불가.
  • HUG 든든전세주택 데이터 제공 형태 — HUG 공고 페이지 구조 및 공공데이터 개방 목록 확인.
  • LH·SH 단지정보 API의 좌표 포함 여부 — 포함되어 있으면 단지 단위는 요약DB 조인 없이 바로 지도에 올릴 수 있다.
01

데이터 파이프라인 설계

공고 메타는 API로, 호실 목록은 첨부파일 파싱으로 얻는 이중 경로. 파싱은 결정적으로 실패할 수 있으므로 실패를 정상 상태로 취급하고 사람이 개입할 지점을 파이프라인 안에 못박는다.

S1
공고 목록 수집
마이홈포털 모집공고 API를 1차 소스로, LH청약플러스 목록 스크래핑을 보조로 사용. 공고 지문(기관+공고명+게시일 해시)으로 중복 제거.
httpx · selectolax · 6시간 주기 크론
S2
상태·마감 추적
LH 목록의 상태·마감일 컬럼을 매 수집마다 대조. 신규/정정공고중/접수마감을 이벤트로 기록해 D-day와 "정정됨" 배지의 근거로 삼는다.
공고 스냅샷 테이블 + diff
S3
첨부파일 수집·형식 분기
XLSX·CSV는 그대로 표로, PDF는 텍스트 레이어 유무 판정 후 표 추출, HWP/HWPX는 XML 변환 경유. 원본 파일은 해시와 함께 보관해 재파싱 가능하게 둔다.
pdfplumber(표) · pypdf(텍스트 레이어 판정) · hwp5/hwpx→XML · openpyxl
S4
호실 레코드 파싱
추출 대상: 주소 · 단지명 · 동 · 호 · 전용면적(㎡) · 보증금/임대료(기본·전세전환·월세전환) · 층 · 방구조 · 승강기 · 비고. 기관·공고유형별 파서를 분리하고, SH 청년매입임대 공개 목록(15102880)을 정답지로 삼아 회귀 테스트한다. 원본 PDF는 해시와 함께 보관해 정정공고로 교체되면 자동 감지한다 — 이것이 "정정됨" 배지의 근거가 된다. PDF 자체는 재배포하지 않고 기관 원문 링크만 건다.
기관별 파서 모듈 · 골든 데이터셋 회귀 테스트
S4b
자격요건 추출
공고문 PDF에는 호실 표만 있는 게 아니다. 입주 자격 · 소득·자산 기준 · 순위 · 가점 · 신청 절차가 함께 실려 있고, 검색 수요는 이쪽이 더 크다("매입임대 소득기준", "행복주택 순위"). 표가 아닌 서술형이라 호실 파서와 별도 경로로 처리하고, 공고 페이지의 자격요건 섹션으로 발행한다.
섹션 헤딩 기반 분할 · 소득분위·자산 기준 수치 추출 · 요약은 검수 큐 경유 필수
S5
정규화
주소는 도로명 우선·지번 병기로 통일, 금액은 정수 원 단위, 면적은 소수 2자리. 유형은 자체 코드로 매핑(행복주택·국민임대·매입임대·장기전세·통합공공임대·전세임대·든든전세).
정규식 + 유형 매핑 테이블
S6
좌표 매칭 (오프라인)
지오코딩 API를 호출하지 않는다. 자체 보유한 위치정보 요약DB 좌표 테이블에 정규화된 도로명주소를 조인한다. UTM-K를 WGS84로 변환해 저장. 매칭 실패 주소는 건물명·지번 보조키로 재시도하고, 그래도 실패하면 읍면동 중심 좌표로 강등한 뒤 geo_precision에 등급을 남긴다.
주소 정규화 → 좌표 테이블 조인 · UTM-K→WGS84 변환 · 정확도 등급(건물/도로/동)
S7
검수 큐
파싱 신뢰도 미달 레코드는 자동 발행하지 않고 큐로 보낸다. 트리거: 표 컬럼 수 불일치, 보증금 0원 또는 10억원 초과, 전용면적 9㎡ 미만·200㎡ 초과, 지오코딩 정확도가 건물 미만, 동일 공고 내 호실 수가 직전 회차 대비 ±50% 변동.
관리자 화면 · 승인/반려 · 반려 사유를 파서 개선에 환류
S8
발행
검수 통과분만 published로 전환해 페이지 생성. 마감된 공고는 삭제하지 않고 closed로 두어 URL을 유지하고, 상단에 마감 배너와 후속 공고 링크를 붙인다.
on-demand revalidate · 사이트맵 갱신
설계 원칙 URL은 한 번 만들면 죽이지 않는다. 마감 공고 페이지도 살려 두는 편이 검색 자산 축적에 유리하고, 벤치마크가 하지 못하는 연도별 공고 아카이브가 그 자체로 새로운 롱테일이 된다.
02

URL · 페이지 구조 설계

  • 지역 페이지 — 매물 3건 이상. 미달 시 페이지를 만들지 않고 상위 시군구 페이지로 301.

  • 자동 생성 문장 비율 — 페이지 본문에서 템플릿 문장이 60%를 넘지 않게 한다. 초과분은 표·지도 등 데이터 블록으로 대체한다.
  • 출처 배지 승계 — 기존 childcare-sample.html의 4종 배지(API 원본 / 계산값 / 자동생성 문장 / 직접 작성)를 그대로 쓴다. 계산값과 자동생성 문장을 시각적으로 구분해야 신뢰도와 심사 방어력이 함께 올라간다.

최종 추천 스택

  • Next.js 15 App Router + ISR — 지역·유형·공고 페이지는 정적 생성, 호실 상세 3만 페이지는 generateStaticParams 없이 온디맨드 ISR(revalidate: 86400). 전량 SSG는 배포마다 수십 분을 태우므로 배제.
  • 네이버 지도 (Web Dynamic Map) — 대표계정에 무료 이용량이 제공되고(API별 월 3,000~1억 건), 지도 데이터 최신성이 카카오보다 낫다고 알려져 있다. 신축 매입임대 비중이 큰 이 도메인에서 실질적인 차이가 된다. 거리뷰는 naver.maps.Panorama로 지원되므로 로드뷰 기능에서도 손해가 없다. 지도 표출은 클라이언트, 마커 좌표는 서버 렌더 HTML에 포함시켜 크롤러가 데이터를 보게 한다.
  • Neon Postgres + PostGIS — 무료 프로젝트 100개라 계정 한도에 걸리지 않는다. "이 지점 반경 1km" 조회를 위해 PostGIS를 켠다.
  • 좌표 원본은 DB 밖에 둔다 — 도로명주소 요약DB 전국본은 수백만 행이라 무료 티어를 넘긴다. 파이프라인 로컬(SQLite/Parquet)에 두고 배치 조인만 수행하고, 매칭에 성공한 좌표만 DB에 적재한다. 호실 3만 행이면 수 MB 규모.
  • Python 파이프라인 레포 분리 — C:\Users\cware\projects\zipgonggo\pipeline\. 프론트와 배포 주기가 다르므로 분리한다.
  • 사이트맵 — sitemap-index.xml + 타입별 분할, 파일당 40,000 URL 상한. 진행중 공고는 priority 0.9, 마감 공고는 0.3.
확인 필요 네이버 Maps 무료 이용량은 대표계정(Maps를 처음 사용한 계정)에만 적용되고 API별로 한도가 다르다. 이 서비스는 지도가 모든 페이지에 뜨므로 지도 로드 수가 곧 페이지뷰다 — 착수 시 콘솔에서 Web Dynamic Map의 실제 월 무료 한도를 확인하고, 월 페이지뷰 목표(30,000)와 대조할 것.

가정과 리스크

  • 가정 1 — 위치정보 요약DB 이용 신청이 승인된다. 공공저작물 제1유형이라 이용 자체는 허용되나, 소관 자치단체·행안부의 이용목적 심사를 거친다. 승인 소요기간이 확인되지 않았다.
    Plan B: 승인 대기 중에는 단지·읍면동 단위 좌표로만 지도를 서비스한다(LH 단지정보 파일의 주소 + 시군구 중심 좌표). 호실 단위 정밀 좌표는 승인 후 소급 적용. Plan C: 카카오 유료앱으로 전환해 실시간 조회 — 다만 마커 수 대비 호출량 때문에 지도 페이지 구조를 클러스터 방식으로 바꿔야 한다.
  • 가정 2 — 공고문 첨부(HWP/PDF)에서 호실 표를 기계적으로 뽑을 수 있다. 표 병합셀·스캔 이미지 PDF·기관별 서식 차이로 실패할 수 있다.
    Plan B: 기관·유형별로 파서를 좁게 만들고, 실패분은 검수 큐로 넘겨 수기 입력. 커버리지가 낮아도 서비스는 성립한다. Plan C: 표 추출을 LLM 보조로 처리하되 검수 큐를 반드시 경유시킨다.
  • 가정 3 — 마이홈포털 API 운영계정 심의를 통과한다. 개발계정 1,000건/일로는 전국 백필이 불가능하다. Phase 1 전체가 이 API에 얹혀 있으므로 가장 무거운 단일 의존이다.
    Plan B: 파일데이터(15088707, 15080989)로 초기 적재하고 API는 증분 수집에만 사용. Plan C: 개발계정 한도 안에서 시도별로 며칠에 나눠 백필.
  • 가정 4 — 공고문 재가공물 게시가 이용약관상 허용된다. 미확인.
    Plan B: 원문 첨부파일은 재배포하지 않고 원문 링크만 제공, 사실 데이터(주소·면적·금액)만 재구성해 게시.
  • 리스크 — 벤치마크의 실내 사진 자산. 사진은 유튜브 촬영으로 축적된 것이라 단기간에 따라잡을 수 없다. 사진 대신 데이터 밀도와 최신성으로 경쟁한다.
  • 리스크 — 자동 생성 페이지의 검색엔진 평가. 얇은 페이지 규칙(§2)을 지키지 않으면 3만 페이지가 전부 저품질로 묶일 수 있다. 색인 페이지 수보다 색인 대비 노출률을 지표로 삼는다.
