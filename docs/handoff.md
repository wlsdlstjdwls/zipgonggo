## 지금 상태 (2026-09-10, 26차 세션)

브랜치 `main`. 사용자가 텔레그램으로 51차 장기전세 단지 상세의 「보증금과 임대료」 표 스크린샷을 보내며
두 가지 지적: ① 최소/최대 요약 줄 때문에 같은 공급유형이 값이 갈리는 것처럼 보이는데 실제론 45㎡/58㎡
전용면적 차이다 ② 계약금 10%/잔금 90% 안내가 없다. 뒤이어 ③ 애초에 장기전세는 전세인데 제목이
"보증금과 임대료"고 표에 "월임대료" 열이 남아 있다고 추가 지적. 셋 다 실제 버그였다.

- **②가 진짜 원인**: `notice_supply`에 공급유형별 실제 계약금(`down_payment`)·잔금(`balance`)이
  이미 DB에 있었다(51차 파서가 원문 표에서 직접 읽어 둠, 확인해 보니 정확히 deposit×10%/×90%).
  그런데 `complexPriceRows`(`web/src/lib/notice-view.ts`)가 이 필드를 아예 안 읽고 버리고 있었다 —
  DB에 있는데 화면에 안 나가던 죽은 데이터. 각 공급유형 base 줄 밑에 계약금/잔금 pay 줄을 붙였다.
  DB 값이 없는 전세형 줄은 공고 단위 `priceRows`와 같은 10%/90% 가정치로 대신한다(이쪽은 fallback만)
- **①**: 공급유형이 정확히 2개일 때 맨 밑 최소/최대 요약 줄이 위 두 줄과 값이 완전히 같아 그대로
  반복하는 구조였다. `priced.length < 3`이면 요약 줄을 안 붙이게 바꿨다(3개 이상일 때만 실제로
  중간값을 요약하는 의미가 있다). note도 "이 단지" → "전체 유형 중"으로 바꿔 위 개별 줄과 구분되게 했다
- **③**: 단지 상세 KPI 카드는 이미 `hasRent`(공급현황에 월임대료 있는 줄이 하나라도 있는지) 기준으로
  "보증금"/"전세금"을 갈라 쓰고 있었는데, 「보증금과 임대료」 h2와 `PriceTable`은 그 신호를 안 쓰고
  항상 고정 문구·3열이었다 — 전세형은 월임대료 열이 매 줄 "—"만 찍히는 채로 남아 있었다.
  `showRent = hasRent || c.min_rent != null`을 만들어 h2와 `PriceTable`(새 `depositHead`/`showRent`
  props, CSS `.ptable.no-rent`로 2열 그리드) 양쪽에 같이 먹였다
- dev(3100) 띄워 실제 렌더 curl로 확인: `<h2>전세금</h2>`, 표가 구분/전세금 2열, 45㎡·58㎡ 각 줄
  밑에 계약금/잔금이 정확한 금액(7,176만/6억 4,584만, 8,892만/8억 28만)으로 붙음. 최소/최대 줄 없음
- 커밋 2개(`9aa36ad` 계약금·잔금 + 최소/최대, `45493ff` 전세금 제목·열), 둘 다 푸시. **프로덕션 curl로
  확인 완료** — `<h2>전세금</h2>`·`ptable no-rent`·계약금/잔금 줄·최소최대 없음 전부 실측 확인

**뒤이어 같은 세션**: 사용자가 "표가 안 예쁘다/보기 힘들다"고 지적 — 계약금·잔금이 유형당 2줄씩이라
표가 늘어지는 게 원인으로 보고, `계약금/잔금` 한 줄에 `"7,176만 원 | 6억 4,584만 원"`처럼 붙여
줄 수를 절반으로 줄였다(`e7755b1`). **그런데 이게 새 버그였다** — 사용자가 스크린샷을 다시 보내며
"금액부분이 잘려서 잘안보야"라고 지적: 합친 문자열이 `.ptable .d`의 `white-space:nowrap` +
`.ptable`의 `overflow:hidden` 때문에 모바일 값 열 폭을 넘기면 끝부분이 그대로 잘려 나갔다
(`6억 4,584만...`에서 "원" 유실). 계약금·잔금을 다시 별도 줄로 되돌렸다(`d079b64`) — 개별 금액
하나만 있으면 폭 안에 들어간다. 줄 여백을 좁힌 CSS(`​.ptable .pay span { padding: 9px }`)는
표를 조금이라도 덜 늘어지게 하는 효과가 있어 그대로 남겼다.
**교훈**: 이 표의 값 열은 nowrap이라 폭이 타이트하다 — 다음에 또 "표를 압축해 달라"는 요청이 오면
텍스트를 옆으로 이어 붙이지 말고(한 줄 길이가 늘어나 잘림 위험), 세로로 줄을 줄이거나 폰트만
줄이는 쪽으로 갈 것. 이번에도 실제 폰 스크린샷으로 뒤늦게 잡았다 — 헤드리스 크롬 캡처(390px 창)는
이 페이지 전체를 오른쪽으로 잘라내는 별개의 캡처 아티팩트가 있어(뷰포트 메타를 안 지키는 듯) 이
표 하나의 폭 문제를 못 짚어냈다. **이 표처럼 값 길이가 빡빡한 곳은 헤드리스 캡처를 믿지 말고
사용자 실기기 스크린샷으로만 판정할 것**

### 21차 세션에서 손댄 것

- **두 지도 줌 불일치** — 공고 상세에 지도가 두 개 있다: 「위치」(`NaverMap`, 핀 하나, 줌 `NAVER_MAP_DEFAULT_ZOOM`=18)와
  「공급 단지」 탐색기(`ComplexMap`, 핀 여러 개). 사용자는 "공고상세 지도"라고 하면 둘 다를 가리키는데, 단지가
  1곳뿐인 공고는 `ComplexMap`이 자체 상수 `SINGLE_ZOOM=15`를 썼다 — 로딩 끝나면 15로 "축소되는 것처럼" 보인 원인.
  `SINGLE_ZOOM`을 `NAVER_MAP_DEFAULT_ZOOM` 참조로 바꿔 맞췄다. 단지가 여럿이라 `fitBounds`를 쓰는 경우는
  핀이 넓게 퍼지면 어차피 다 보이게 줄여야 해서 완전히 통일은 안 되지만, 반대로 핀들이 아주 가까이 모여
  `fitBounds` 결과가 18보다 더 확대되는 경우엔 18로 캡을 걸었다(`complex-map.tsx`)
- **그런데도 "여전히 똑같다"** — 스크린샷으로 받은 사례(파주~이천까지 62개 단지, 20km 축척)는 애초에
  핀 전부를 담으려면 넓게 축소할 수밖에 없는 경우라 위 캡은 적용되지 않는다. 이건 숫자를 맞춰서 될 문제가
  아니라 **로딩 중 순간적으로 보이던 프레임**이 문제였을 가능성이 크다: 마커 동기화 + `fitBounds`가
  `useEffect`(브라우저 페인트 다음 틱)에 있어서, `.cx-load` 오버레이가 걷히는 첫 페인트엔 아직 마운트 때
  줌(서울 좁게, `SEOUL_ZOOM=11`)이 남아 있다가 그다음 틱에 fit 결과로 튀는 게 "로딩 끝나고 또 축소된다"로
  보였을 수 있다. `useLayoutEffect`로 바꿔 같은 커밋의 페인트 전에 fit까지 끝내도록 고쳤다 —
  **역시 브라우저로 재현·확인은 못 했다**, 배포 뒤 실제로 나아졌는지 확인 필요
- **그래도 계속 더 축소된 화면이 남았다** — 사용자가 "이렇게 나와야 하는데"(10km 축척, 좁게)와
  "아직도 이렇게 나온다"(20km 축척, 넓게) 스크린샷을 같이 보내옴. 둘 다 같은 공고(62단지)인데 축척이
  정확히 2배 차이 — 컨테이너 크기 자체가 fitBounds 계산 시점마다 달랐다는 뜻.
  범인은 `--cx-h: min(780px, calc(100vh - 132px))`의 `100vh` — 모바일에서 주소창이 접히기 전(좁을 때)
  기준으로 굳어진 값이다. `fitBounds`는 마커 집합이 바뀔 때 딱 한 번만 돌고, 그 뒤 컨테이너가 커져도
  `ResizeObserver`는 지도에 리사이즈(재도색)만 알리고 다시 fit하지는 않았다 — 그래서 좁았던 순간의
  확대율(더 축소된 쪽)이 그대로 굳어 남았다.
  - `globals.css`: `--cx-h` 계산을 `100vh` → `100dvh`(주소창 접힘/펼침에 실시간으로 반응하는 단위)로
  - `complex-map.tsx`: 마커 동기화 이펙트의 fit 로직을 `fit()` 함수로 뽑아, 리사이즈 옵저버 콜백에서도
    다시 부른다. 단, 사용자가 이미 단지를 하나 골라 보고 있으면(`selectedId !== null`) 다시 fit하지
    않는다 — 그 상태에서 시점이 훅 바뀌면 안 되니까
  - **역시 브라우저 확인 못 했다.** 특히 이 가설(`100vh` 불안정)이 실제 원인인지는 모바일 실기기에서만
    확인 가능하다 — 다음 세션이나 사용자 재확인이 필요
- **배포 확인하고 나서야 진짜 원인에 가까워졌다** — `curl`로 프로덕션 CSS를 직접 받아 `100dvh`·
  `.cx-load.hide{...animation:none}` 둘 다 떠 있는 걸 확인했다(배포는 맞았다). 그런데도 사용자가
  "똑같다"고 해서, 이 공고(sh-2026-309337-haengbok, 행복주택 2차, 62단지)의 실제 주소를 프로덕션
  HTML에서 직접 긁어봤다 — **62곳 전부 서울 25개 구 안**(경기·인천 주소 0건). 스크린샷에 찍힌
  동두천·포천·파주 같은 지명은 핀이 아니라 그 줌에서 네이버 지도가 그리는 배경 지명 라벨이었다.
  즉 20km 축척까지 벌어질 지리적 이유가 없었다 — `fitBounds`가 쓰는 컨테이너 크기 자체가 틀렸다는 뜻.
  범인으로 새로 지목한 건 `map.getSize()` — 네이버 SDK가 지도 **생성 시점**에 잰 크기를 내부에 캐시해
  두고, 그 뒤 레이아웃이 자리 잡아도 `resize` 이벤트를 명시적으로 걸지 않으면 갱신 안 될 수 있다.
  `fit()`에서 `map.getSize()` 대신 `el.current.getBoundingClientRect()`로 DOM 실측 크기를 직접 읽고,
  `fitBounds` 직전에 `Event.trigger(map,"resize")`를 한 번 강제로 건다(`complex-map.tsx`).
  **이번에도 브라우저 확인 못 함** — 이 이론이 맞는지는 배포 뒤 실측으로만 알 수 있다

- **"지도 로딩 끝나도 로딩화면이 안 사라진다"** — `globals.css`의 `.cx-load`가 `animation: cx-load-in 260ms both`
  로 등장하는데, `both`가 `opacity: 1`을 계속 붙들고 있었다. `.hide`가 `opacity: 0`을 트랜지션으로 걸어도
  트랜지션은 "진행 중"에만 우선순위를 갖고, 끝나면 여전히 살아있는 진입 애니메이션의 고정값(1)으로 되돌아간다 —
  잠깐 옅어지는 듯하다 도로 튀어 돌아오는 모양. 19차의 지도 페이드인 버그(ed18f40)와 같은 종류인데
  이번엔 반대 방향(사라져야 할 때 애니메이션이 안 놓아주는 쪽)이었다.
  `.cx-load.hide`에 `animation: none`을 추가해 애니메이션을 놓아주고 트랜지션 값이 그대로 남게 고쳤다.
  실제 브라우저로 재현·확인은 못 했다(이 세션엔 브라우저 도구가 없었다) — 배포 뒤 육안 확인 필요
- 같은 계열(진입 애니메이션 `both` + 이후 클래스로 같은 속성 토글)이 다른 곳에도 있는지 훑었다.
  `.map`·`.cx-map > .canvas` 등은 19차에서 이미 "등장만 하고 이후 토글 없음" 구조로 정리돼 있어 해당 없음.
  `.cx-load`만 유일하게 진입 애니메이션과 이후 hide 토글이 같은 속성(opacity)에서 겹쳐 있었다

## 함정 (겪은 것만)

### dev 서버

- 사용자가 **3100 포트에 `npm run dev`를 켜 둔 채** 작업한다. `next build`를 돌리면 `.next`를 덮어 500이 난다.
  검증은 `npx tsc --noEmit`으로 한다
- 파일을 **삭제**하면 dev의 모듈 그래프가 상해 전 페이지가 500이 된다(`Failed to read source code from …`).
  touch로는 안 풀린다 — dev를 내리고 `.next/server .next/static .next/cache`를 지운 뒤 다시 띄운다
- 마이그레이션 뒤 `column does not exist`는 스키마가 아니라 오래 켜 둔 dev의 옛 커넥션 탓이다
- `unstable_cache`(예: `getEligibilityRules`, 1시간)로 감싼 쿼리는 **DB를 고쳐도 dev가 계속 옛 값을 보여준다.**
  dev 재시작만으론 안 풀린다(파일시스템에 캐시가 남는다) — `.next/cache`를 지우고 나서 재시작해야 반영된다(2026-09-09).
  프로덕션은 `.next/cache`를 못 지우니 20차에서 `POST /api/revalidate`(`x-revalidate-secret` 헤더)를
  만들었다 — DB를 고친 뒤(수동이든 파이프라인이든) 이걸 부르면 즉시 반영된다. 값은 `docs/data-sources.md`

- `s3_sh_complex`가 `no_attachment`로 건너뛰면 **`--cached`를 먼저 쓴다.** `pipeline/data/ish/{seq}/`에
  받아 둔 쪽 XML을 네트워크 없이 다시 읽는다. 파서를 고친 뒤 되돌려 넣을 때의 기본 경로다
- `replace_notice_complexes`는 DELETE + INSERT다. **좌표는 임시표로 업어 넘긴다**(2026-09-09 추가) —
  안 그러면 S3 재실행 한 번에 좌표 262건이 날아간다. 주소가 바뀐 행은 못 업어 오므로 S6을 다시 돌린다
- 별첨 금액 6칸이 한 칸으로 붙어 오면 자릿수가 이어져 `bigint out of range`가 난다. 상한 1,000억으로 잘라 버린다
- 파이프라인 실행은 `cd pipeline && PYTHONPATH=src python -m zipgonggo_pipeline.stages.<이름>`.
  접속 문자열은 `pipeline/.env`, 마이그레이션은 `python db/migrate.py`

## 표기·태도 (CLAUDE.md 보충)

- 값이 없으면 감추지 말고 **「준비 중」**이라고 쓴다(`components/pending.tsx`, `Kpi`의 `off`).
  왜 비었는지 말해 주지 않는 빈칸을 만들지 않는다
- 접수 날짜를 못 읽은 공고는 **「원문 확인」**(`lib/format.ts` `NO_DATE`).
  기관 목록의 「모집중」을 날짜 자리에 대신 쓰지 않는다
- 공고문 용어는 `lib/glossary.ts`에 뜻을 두고 `<Term>`으로 걸어 페이지 밑 「용어 설명」으로 잇는다.
  새 용어를 화면에 쓰면 사전에도 넣는다
- 틀린 값을 싣느니 비워 둔다. 파서에 검문(`_plausible` 류)을 두고 통과한 줄만 적재한다
