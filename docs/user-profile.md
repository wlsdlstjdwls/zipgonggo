# 「내 조건」 한 벌 — 자격진단 입력값의 저장 규칙

자격진단에 넣는 값(나이, 가구원 수, 소득, 자산, 거주지, 계층 등)을 어디에 두고 어떻게 나르는지.
결정 근거는 2026-09-22 사용자 요청과 그때의 검토다. 화면 문구와 법적 문서는 이 규칙을 따라간다.

## 왜 만들었나

입력 화면이 셋인데 서로를 몰랐다.

| 화면 | 프로필 타입 | 저장 |
|---|---|---|
| `/eligibility` 자가진단 | `lib/eligibility.ts`의 `Profile` | **없었다** — 들어올 때마다 기본값 |
| 공고 상세 「내 조건에 맞는 단지」 | `lib/notice-fit.ts`의 `FitProfile` | `zipgonggo.fit.v1` |
| 민간임대 「내 조건에 맞는 주택형」 | `lib/mingan-fit.ts`의 `MinganProfile` | `zipgonggo.fit-mingan.v1` |

같은 사람이 같은 소득을 세 번 넣었다. 번거로움의 실체는 「계정 저장이 없어서」가 아니라
**세 폼이 한 사람을 세 사람으로 본 것**이었다.

## 지금 구조

```
lib/profile.ts          UserProfile 한 벌 + 어댑터(toElig/fromElig, toFit/fromFit, toMingan/fromMingan)
components/profile-context.tsx   한 벌을 앱 전체에 물리고, 로컬과 서버 사본을 맞춘다
api/profile/route.ts    GET(읽기) PUT(저장 켜기·고치기) DELETE(끄기)
user_profile            회원 한 명당 한 행. **행이 있으면 계정 저장이 켜진 것이다**
```

- **기본은 브라우저다.** `zipgonggo.profile.v1` 한 자리에 두고 세 화면이 같이 쓴다.
- **계정 저장은 기본 꺼짐인 선택 기능.** 로그인만으로는 아무것도 서버로 가지 않는다.
  켜는 자리는 `/my/account`의 「자격진단 조건 저장」 하나다.
- 공고마다 갈리는 값(공급 구분, 면적, 계층, 신청유형, 1순위 자격)은 **한 벌에 넣지 않는다** —
  다음 공고에 들고 가 봐야 없는 값이라 지금처럼 `zipgonggo.fit.v1`에 남는다.

### 값이 오가는 순서

1. 서버 HTML은 **언제나 기본값**이다. 하이드레이션이 어긋날 자리를 만들지 않는다
2. 마운트 뒤 localStorage를 읽어 즉시 채운다
3. 로그인했고 저장이 켜져 있으면 `/api/profile`을 한 번 묻고, **서버 쪽이 더 최신일 때만** 갈아끼운다
4. 사람이 이미 손을 댔으면(`dirty`) 서버 답이 늦게 와도 덮지 않는다
5. 쓰기는 1.2초 디바운스 + 탭을 떠날 때 flush. 서버 쓰기가 실패해도 화면은 그대로 간다

관심 공고(★)와 **다른 점**: 목록은 합집합이 되지만 조건은 값이 하나뿐이라 합칠 수 없다.
그래서 갱신 시각으로 가르고, 갈아끼울 때 토스트로 알린다.

## 본인 칸과 세대 칸은 따로 든다

시드(`supply_type`)가 자격을 **두 층**으로 적어 둔다. 한 칸으로 받으면 판정이 틀린다.

| 축 | 「본인」 기준 | 「세대」 기준 | 프로필 칸 |
|---|---|---|---|
| 무주택 | 8개 (청년 계열) | 24개 | `homelessSelf` / `homeless` |
| 자산 | 5개 (`happy_student` `happy_youth` `ys_youth` `ys_priv_youth` `buy_youth`) | 17개 | `assetSelfMan` / `assetMan` |
| 소득 | 3개 + `본인+부모` 1개 + `청년특공_분기` 2개 | 19개 | `incomeSelfWon` / `incomeHouseholdWon` |

소득은 처음부터 두 칸이었는데 무주택과 자산은 한 칸이었다. **부모가 집을 가진 청년이
행복주택 대학생과 청년 매입임대까지 전부 미달로 떨어졌다**(2026-09-22 정정).
같은 사람(25세 대학생, 본인 무주택·자산 500만, 세대 유주택·자산 5억)으로 재 보면 통과 0개 → 8개다.

- 엔진은 `t.homeless_scope === "본인"`일 때 `homelessSelf || homeless`로 본다 — 세대가 무주택이면 본인도 무주택이다
- `asset_scope === "무관"`인 10개는 `asset_limit_man`이 전부 null이라 애초에 안 본다
- **옛 저장분은 `sanitizeProfile`이 세대 값을 본인 칸에 복사한다.** 기본값을 넣으면
  「세대에 집이 있다」고 적어 둔 사람이 본인 무주택으로 바뀌어 판정이 조용히 달라진다
- 화면에서 두 칸은 서로를 거스를 수 없다 — 본인이 유주택이면 세대도 유주택이고, 본인 자산은 세대 자산을 넘지 못한다

`대학생`과 `취업준비생`은 **새 칸이 아니라 계층 칩이다.** `required_class`와 `age_exempt`에 이미 있다.

## 서버에 올리지 않는 것

`SENSITIVE_KEYS` = `disabledSelf` | `disabledFamily` | `special`
`SENSITIVE_CLASSES` = 장애인 | 국가유공자 | 북한이탈주민

건강(상이등급)이나 출신과 이어지는 값이라 민감정보 무게로 다룬다. **브라우저에는 그대로 남아
진단은 똑같이 돌고, 서버 사본에서만 빠진다.** 거르는 자리가 둘이다 — 브라우저가 `stripSensitive`로
빼고, 서버가 `sanitizeProfile(…, false)`로 또 뺀다. 브라우저를 믿지 않는다.

이 목록을 **줄이려면 개인정보처리방침 3항과 별도 동의부터 손본다.** 늘리는 건 코드만 고치면 된다.

## 검증과 상한

`sanitizeProfile`이 유일한 문이다. 모르는 키는 버리고, 수치는 **화면의 min/max와 같은 범위**로 자르고,
계층은 개수(16)와 길이(30자)를 끊는다. DB에도 `pg_column_size(data) < 4096` 제약이 있다 —
프로필 한 벌은 1KB가 채 안 되니 4KB를 넘겼으면 우리가 만든 값이 아니다.

## 거주지 어휘가 셋이다

| 화면 | 고르는 말 |
|---|---|
| 자가진단 | 서울 자치구 \| 연접 시군구 이름(광명시 등) \| "그 외 지역" |
| 공공 공고 | 서울 자치구 \| "연접" \| "경기기타" \| "기타" |
| 민간임대 | 서울 자치구 \| "기타" |

그래서 한 벌이 `region`(자가진단 어휘)과 `gu`(공고 폼 어휘) **두 칸을 다 든다.**
각 화면이 제 칸에 쓰고, 건너편 칸은 **애매하지 않을 때만** 따라 고친다 —
「연접」에서 「광명시」를 되살릴 수는 없으니 그럴 땐 건드리지 않는다(`regionToGu` / `guToRegion`).

## 보유와 파기

| 언제 | 무엇 |
|---|---|
| 탈퇴 | `user_account` CASCADE로 같이 삭제 |
| 저장 끄기 | `DELETE /api/profile` — 서버 사본만. 브라우저 값은 남는다 |
| 24개월 미갱신 | `/api/cron/purge-profiles`가 파기(`PROFILE_RETAIN_MONTHS`) |

`PROFILE_RETAIN_MONTHS`는 **개인정보처리방침 3항에 적은 숫자와 같아야 한다.**

## 시행일 자물쇠

`PROFILE_SYNC_START`(= 2026-09-29) 전에는 계정 저장이 **화면에도 없고 서버도 안 받는다**(`PUT` 409).
수집 항목이 느는 개정이라 방침 11항의 「7일 전 공지」를 지킨 것이다.

**그날이 지나면 할 일이 셋이다.**

1. `PRIVACY_AMENDED_DATE`를 `2026-09-29`로 올린다
2. 방침 3항·11항, 약관 부칙의 「…부터」 예고 문장을 현재형/이력으로 고친다
3. `TERMS_EFFECTIVE_DATE`를 `2026-09-29`로 올린다 — 그날 이후 로그인하는 회원의 `terms_version`이 새 날짜로 찍힌다

## 운영자 콘솔

`/admin/members`에 **저장을 켠 회원 수만** 낸다. 무엇을 저장했는지는 그리지 않는다 —
운영자가 남의 소득을 들여다보는 화면을 만들지 않는다(방침 3항의 약속).
